# 실험 기록과 대용량 자료 보존 절차

Document status: **Reference**

Last reviewed: 2026-09-06

## 목적과 적용 상태

실험의 결론을 검토할 수 있는 원본 증거와 재실행에 필요한 입력을 보존하면서,
종료된 실험마다 생긴 대용량 실행 디스크를 무기한 쌓아두지 않기 위한 절차다.
2026-09-06 사용자가 실험 문서화 후 불필요한 복제본 정리를 요청했고, 이 절차를
두 완료 캠페인에 수동 적용했다. 이어서 사용자가 더 나은 방식을 구현해도 된다고
요청하여, 검증한 두 하네스 형식에 한정된 계획/실행 도구를 구현했다.
자동 보존 기간이나 무인 삭제 서비스를 켠 것은 아니다.

상위 규칙은 [AGENTS.md](../../AGENTS.md)와
[개발 체계](../development-system.md)다. 이 문서는 실험 기준·제품 상태·증거
순위를 바꾸지 않는다. 실제 적용 결과는
[2026-09-06 정리 기록](../history/windows-hvf/experiment-storage-cleanup-20260906.md)에 있다.

## 기록을 보존한다는 의미

요약문은 증거의 위치와 의미를 설명한다. 측정 원본이나 영수증을 대체하지 않는다.
가령 “20회 성공”만 남기면 어떤 바이너리, 입력, 전원 조건에서 무엇을 측정했는지,
개별 실행의 성공과 캠페인 판정이 같은지 확인할 수 없다.

반대로 실행마다 생성한 전체 Windows 디스크를 모두 보유해야 로그나 수치를
검증할 수 있는 것도 아니다. guest 결과 파일을 이미 추출했고 다른 실험의 입력으로
사용하지 않는 출력 복제본은, 삭제 후 가능한 검증과 불가능한 검증을 명시해 정리한다.

## 자료별 처리 기준

| 자료 | 기본 처리 | 정리 전에 필요한 확인 |
| --- | --- | --- |
| 기준 VM 이미지·서명된 입력·라이선스 출처 | 보존 | 이 절차는 canonical input 삭제를 승인하지 않는다 |
| 현재 사용자 VM·복구 키·vTPM 상태 | 보존, 비공개 | 저장 위치가 실험 폴더라는 이유로 지우지 않는다 |
| 진행 중인 실험의 disk/vars | 보존 | 프로세스 종료와 queue 종료 상태를 모두 확인 |
| 미해결 오류 재현용 디스크 | 보존 | 로그만으로 설명 가능한지, 추가 메모리/디스크 분석이 필요한지 판단 |
| 완료된 실험의 출력 복제본 | 조건부 정리 | 입력 관계·원본 증거·의존성·대표 사례·복구 한계를 문서화 |
| 개별 실패·캠페인 STOP 기록 | 보존 | 삭제 결정이 실패 기록을 제거하거나 성공으로 바꾸지 않도록 확인 |
| receipt·측정 raw JSON·로그·스크린샷 | 원본 보존 | 해시 목록 작성, 공개 자료와 비공개 자료 분리 |
| 빌드 캐시·임시 컴파일 산출물 | 재생성 가능하면 정리 | Git 미추적 여부, 실행 중인 소비자, 봉인된 바이너리와 구별 |
| 수정된 의존성 checkout | 보존 | 중첩 Git 저장소의 미커밋 수정 및 패치 출처 확인 |

파일명이 cache, work, tmp이거나 오래되었다는 사실만으로 삭제 대상이 되지 않는다.
prepared 디스크도 다른 manifest의 입력이면 보존한다. vars 파일이 작다고
하더라도 디스크와의 관계는 기록해야 한다. vars만 남겨서 삭제된 disk 상태를 복원할 수는 없다.

## 저장소와 로컬 자료의 역할

본 개발 저장소에는 다음을 남긴다.

1. 실험 목적, 가설, 표본 수와 사전 임계값, 결과 해석, 다음 작업의 허용/금지 범위.
2. 소스/하네스 커밋, 공개 가능한 입력 및 receipt 해시, job ID, 실행별 정리 여부.
3. 삭제 이유, 보존 위치를 찾는 규칙, 실제 회수 공간, 검증 범위와 알려진 한계.
4. 원본 증거가 없어지거나 입력을 재현할 수 없게 됐을 때 영향받는 결론.

로컬 workspace에는 개인 경로가 포함된 inventory, 원본 로그·측정값,
guest 상태와 삭제 journal을 둔다. 공개 문서는 로컬 데이터의 복제 저장소가 아니다.
게스트 디스크, vars, vTPM, 복구 키, 타사 콘텐츠를 Git이나 CI artifact에 넣지 않는다.
로그도 개인정보·자격증명 여부를 검토하지 않고 공개하지 않는다.

현재 로컬 인덱스는 사용자 홈 아래 BridgeVM-Workspace이고, lab 자산의 호환 경로는
사용자 홈 아래 BridgeVM 심볼릭 링크다. 절대 개인 경로를 공개 문서의 재현 조건으로
고정하지 않고 job ID·상대 경로·해시로 관계를 설명한다.

## 삭제 전 절차

1. 범위를 정한다. 캠페인 ID, 정확한 job ID, 단일 파일 상대 경로를 명시한다.
   workspace 전체나 패턴 기반 재귀 삭제를 대상으로 삼지 않는다.
2. 실행 중인 큐와 프로세스를 확인한다. 완료 폴더에 있다는 사실만으로 종료를
   단정하지 않고 job/result/cleanup 기록을 함께 읽는다.
3. 해당 실행 커밋의 스크립트에서 출력 디스크 생성 경로를 확인한다. 입력 원본과
   출력의 inode가 다르고, 각 lane이 독립 disk/vars를 사용했는지 확인한다.
4. 입력 manifest와 source checkout을 보존한다. 현재 입력 전체 해시를 다시
   계산했는지 별도 표시한다. 과거에 검증한 해시는 최신 검증으로 간주하지 않는다.
5. guest 결과를 추출했는지 확인한다. receipt에 기록된 result/raw/완료 marker 해시를
   대조하고 나머지 보존 파일의 해시를 기록한다. CRLF 로그 파싱은 정규화한 뷰에서
   수행하되 보존 원본은 바꾸지 않는다.
6. 다른 입력 manifest가 삭제 대상의 현재 경로나 실행 당시 경로를 참조하는지
   확인한다. 경로 검사만으로 다른 이름의 모든 의존성을 발견할 수는 없으므로
   input/output의 역할도 함께 검토한다.
7. 대표 디스크를 선택한다. 2026-09-06에는 두 캠페인 모두 순번 1을 선택했다.
   가장 빠르거나 가장 보기 좋은 결과를 골라 증거를 왜곡하지 않는다.
8. 삭제 목록과 문서를 먼저 저장한다. 디스크 stat, 최종 전체 해시 유무, 보존 파일
   해시, 입력 경로/기록된 해시, 정확한 상태 복구 가능 여부를 기록한다.

대표 디스크 하나는 나머지 삭제 디스크의 백업이 아니다. 오류 조사에 여러 서로 다른
상태가 필요하면 대표 개수를 늘리거나 정리를 보류한다. “모든 캠페인은 1개면 충분”이라는
일반 규칙으로 확대하지 않는다.

## 실행과 사후 검증

삭제 도구는 명시된 파일 경로만 다루고, 삭제 직전에도 경로·inode·크기·수정 시각이
목록과 같은지 확인해야 한다. symlink나 예상 밖의 hard link, 활성 실행, 변경된
증거가 있으면 중단한다. 파일마다 삭제 의도와 완료를 기록해 중간 실패도 남긴다.

정리 후 보존 파일을 다시 해시 검증하고, 대표 디스크와 입력의 존재, 삭제 파일의
부재를 확인한다. 공간 측정은 동일한 볼륨의 실제 가용 블록을 사용한다.
APFS clone의 파일 크기·할당 블록 합계는 독점 점유량이 아니므로 회수 예상치로 쓰지 않는다.
다른 프로세스의 쓰기와 APFS 공간 회수 시점 때문에 측정값은 약간 변할 수 있다.

삭제 실패나 검증 실패가 발생하면 남은 파일을 추가 삭제하지 않고 journal을 읽는다.
이미 삭제된 파일을 되살렸다고 주장하거나 실패한 기록을 덮어쓰지 않는다.
재개는 완료된 삭제와 남은 대상을 다시 구분한 명시적 목록으로 수행한다.

## 재현성과 복구의 차이

| 보존 상태 | 가능한 작업 | 보장하지 못하는 것 |
| --- | --- | --- |
| 원본 로그·측정값·receipt | 과거 수치와 판정 재검토 | 삭제 디스크를 다시 부팅해 조사 |
| 입력 원본·정확한 커밋·설정 | 입력 재검증 후 새 실험 구성 | 과거 시각·타이밍·최종 상태의 동일 재생 |
| 대표 출력 disk와 해당 vars | 그 대표 실행 상태 조사 | 삭제된 다른 실행 상태 복구 |
| 삭제 journal·stat·해시 목록 | 무엇을 삭제/보존했는지 확인 | 삭제된 원본 바이트 복원 |

image_sha256 같은 필드가 실행 전 입력을 가리키면 최종 디스크 해시라고 부르지 않는다.
벤치마크 결과의 final_sha256도 workload 데이터의 해시일 수 있다. 필드의 의미를
스키마와 writer에서 확인해야 한다. 해시 자체는 데이터 백업이 아니다.

## 다음 실험의 최소 기록 양식

- 식별: 날짜, 담당자, 가설/이슈, campaign/job ID, 진행/완료/무효 상태.
- 조건: 정확한 커밋과 바이너리 해시, 입력 manifest 해시, 하드웨어·OS·전원·메모리·vCPU.
- 설계: workload·표본 수·순서·사전 threshold·중단 규칙·비교군의 차이.
- 결과: 전체 표본과 실패, 계산 방법, 판정, 해석 가능한 범위와 금지되는 주장.
- 근거: 원본 receipt·측정·로그 위치와 해시, 누락 자료, 현재 입력 검증 여부.
- 재실행: 사용할 기존 tier, 입력을 구하는 경로, 독립 clone/vars 준비, 예상 공간.
- 보존: 대표 사례, 미해결 재현 상태, 정리할 출력 목록, 삭제/복구 한계.
- 마감: 전후 공간, 보존 파일 재검증 결과, 관련 문서와 다음 검토 조건.

## 구현한 반복 사용 도구

[archive-experiment.py](../../scripts/archive-experiment.py)는 plan과 apply를 분리한다.
plan은 큐/미디어를 변경하지 않고, 지정한 새 파일에 비공개 inventory를 작성한다.
apply는 그 파일의 SHA-256을 요구하고 현재 상태에서 inventory를 다시 생성해
일치 여부를 확인한다. 수정된 계획에 원본 경로를 끼워 넣어 삭제할 수 없도록 한다.
계획이나 journal을 기존 파일에 덮어쓰지 않는다.

```sh
python3 scripts/archive-experiment.py --queue-root /absolute/private/live-queue plan \
  --campaign a40f06e9d0835f324f413371fed57d75 \
  --out /absolute/private/archive/plan.json
```

위 경로들은 사용자 환경에 맞춰 바꿀 예시다. 도구가 출력하는 candidates 수와
plan 파일의 보존/삭제 목록 및 SHA-256을 검토한 뒤, 실제 정리가 필요할 때만 실행한다.

```sh
python3 scripts/archive-experiment.py --queue-root /absolute/private/live-queue apply \
  --plan /absolute/private/archive/plan.json \
  --plan-sha256 SHA256_FROM_PLAN_OUTPUT \
  --journal /absolute/private/archive/deletions.jsonl
```

apply는 일반 live worker와 같은 worker.lock을 확보하며 기존 lock을 탈취하지 않는다.
대기/실행 job 및 cleanup fence가 있으면 거부하고, lsof로 삭제 대상의 열린 파일
사용을 확인한다. 이 확인이 실패하거나 lsof가 없으면 삭제하지 않는다. 파일별
identity 재검증과 intent/deleted journal을 기록한 후, 보존 파일과 대표·입력을
다시 검사한 complete 이벤트를 남긴다. 중간 실패는 자동 재시도하지 않는다.

이 도구가 현재 지원하는 형식은 T15의 하네스 799dcf345a05dbf8b272354f987fcec8f2b23bd0와
T16 v1의 하네스 3ffb66b1608b1a69ad0d2dae579c9bb59f1aadba다. 모두 20개 valid 개별
실행과 고유 순번 1–20을 요구한다. 순번 1은 반드시 디스크가 남아 있어야 하고,
나머지 중 이미 없는 파일은 already absent로 표시한다. 다른 하네스·표본 수·실패한
실행이 있는 캠페인은 지원을 검토하기 전까지 거부한다. 이는 캠페인 판정을 pass로
바꾸기 위한 조건이 아니라 현재 검증된 정리 범위를 제한하는 조건이다.

source 입력 전체 해시는 매번 다시 계산하지 않는다. recorded hash와 현재
identity를 기록하며 계획 이후 변하면 거부하지만, 과거 원본과 현재 바이트의 동일성을
새롭게 보증하지 않는다. 원본이 변했을 가능성이 있는 경우 별도 전체 해시 검증이
필요하다. 전체 최종 디스크 해시 및 복구 백업도 생성하지 않는다.

관련 테스트는 [실험 정리 테스트](../../tests/integration/experiment-retention-test.py)다.
합성 임시 파일만 사용해 정상 정리, source/대표/vars 보존, 변조한 계획, 변경된 증거와
입력, 활성 큐/lock, symlink/hardlink, 다른 manifest 의존성, 불완전/실패 캠페인,
잘못된 계획 해시, 열린 디스크를 검사한다. Python project gate에서 self-test를
실행하므로 GitHub-hosted CI에서도 결정적으로 실행된다. 실제 VM을 켜지 않는다.

## 남은 자동화 제안

공개용 상세 설명과 원본 증거의 privacy 검토는 아직 자동 생성하지 않는다.
다른 tier를 지원하려면 출력 소유권과 receipt 의미를 검토하고 별도 테스트를 추가한다.
기한 만료에 따른 자동 삭제, 실패 실험 자동 정리, 원본 이미지 중복 제거는 구현하지
않았다. 외부 수동 프로세스나 큐를 우회하는 다른 프로그램의 모든 동시 변경까지
막는 전역 파일시스템 잠금은 아니므로 조용한 작업 환경에서 실행해야 한다.
